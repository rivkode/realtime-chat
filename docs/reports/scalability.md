# 수평 확장 전략

## 문제

서버 수평 확장 시 세션을 어떻게 분산하고 상태를 어디에 저장하는가. 전통적 접근은 세션을 특정 서버에 고정(session affinity)하지만, 그러면 "어느 세션이 어느 서버에 있는지" 추적 매핑이 필요하고 그 서버가 죽으면 세션 전체가 영향받는다.

## 접근 — "세션을 서버에 배치하지 않는다"

본 설계의 답은 **세션을 특정 채팅 서버에 배치(소유)시키지 않는 것**이다. 채팅 서버는 어떤 세션도 소유하지 않는다. 한 세션의 두 유저가 서로 다른 서버에 흩어져도 무방하다 — 모든 라이브 전달이 `channel:session:{id}`라는 Redis 채널을 경유하기 때문이다([실시간 라이브 전달](realtime-delivery.md)).

세션이라는 도메인 개념을 서버에 매핑하는 대신 **채널로 추상화**했다. 그 결과:

1. 세션-서버 매핑 테이블이 불필요하다.
2. 신규 연결을 단순 least-connection으로 분배해도 된다 — 어느 서버에 붙든 상관없으므로.
3. 서버 장애가 "그 서버의 연결 재수립"으로 끝나고 "세션 마이그레이션"이 필요 없다.

## 계층별 확장 기준

| 계층 | 확장 기준 | 전략 |
|---|---|---|
| API 서버 | QPS | 무상태 → 로드밸런서 뒤 단순 증설 |
| 채팅 서버 | 동시 연결 수 | least-connection으로 신규 연결 분산. 서버 간 전달은 Redis 세션 채널이 중계 |
| MongoDB | 데이터량·쓰기 부하 | `events`를 `session_id` shard key로 샤딩 |
| Redis | 처리량·채널 수 | 클러스터 모드 — 단 Pub/Sub fan-out에 한계 |

## 상태 저장 — 무엇을 어디에 두는가

| 상태 | 저장 위치 | 휘발성 |
|---|---|---|
| 대화·세션·스냅샷 | MongoDB (`session_id` 샤딩으로 분산) | 영속 |
| presence | Redis (TTL) | 휘발 |
| WebSocket 연결·세션 매핑 | 채팅 서버 인메모리 | 휘발 (연결의 부산물) |

**확장 가능한 상태는 어느 것도 채팅 서버 인메모리에 영속적으로 두지 않는다**는 것이 핵심이다. 채팅 서버 인메모리의 연결 테이블(`ConnectionRegistry`)은 살아있는 연결의 부산물일 뿐 — 서버가 죽으면 그 연결들도 함께 끊기므로 복구 대상이 아니다.

## 신규 연결 분배 — least-connection

WebSocket은 한 번 맺으면 오래 유지되는 연결이라, 신규 접속을 어느 채팅 서버로 보낼지 정하는 메커니즘이 필요하다.

| 안 | 분배 근거 | 평가 |
|---|---|---|
| L4 LB 라운드로빈 | 순번 | WebSocket의 연결 수 편향을 못 잡음 — 라운드로빈은 "연결 맺는 순간"만 고르게 나누고 현재 연결 수는 안 봄 |
| **L4 LB least-connection (채택)** | LB가 보는 활성 연결 수 | 라운드로빈의 편향 문제 해결. LB 기본 기능이라 추가 구현 0 |
| Redis 레지스트리 + API 서버 선택 | 채팅 서버가 보고한 `conn_count` | 가장 정밀하나 별도 레지스트리 계층 + 정합성 관리. 현 범위엔 과설계 |

least-connection은 nginx·HAProxy·클라우드 LB가 기본 제공하므로 별도 코드 없이 라운드로빈의 편향 문제를 해결한다. 로드 밸런서는 인프라 계층이라 구현 대상이 아니며 설계 문서로 결정을 기술한다.

> **전환 지점** — 채팅 서버별 *활성 WebSocket 세션 수*를 애플리케이션 레벨 지표로 더 정밀하게 분배해야 하면 Redis 레지스트리 기반 디스커버리로 전환한다. 그 경우 채팅 서버가 `conn_count`를 TTL과 함께 Redis에 등록하고, 이 레지스트리 키 만료를 서버 생사 판정에도 활용한다.

## 확장의 진짜 천장 — Redis Pub/Sub

MongoDB 샤딩은 `events`의 무한 성장을 잘 흡수한다 — `session_id` shard key로 쓰기가 분산되고, 세션 단위 조회·복원이 단일 샤드에서 완결돼 scatter-gather를 피한다.

그러나 **이 설계의 확장 한계는 MongoDB가 아니라 Redis Pub/Sub이다.** Redis Pub/Sub은 단일 노드 fan-out 모델이라, 클러스터 모드를 써도 일반 Pub/Sub 메시지는 전 노드에 전파되어 샤딩 이점이 적용되지 않는다(Redis 7.0의 샤드 한정 `SSUBSCRIBE`가 이 때문에 도입됨). 채팅 트래픽이 늘면 Redis Pub/Sub의 fan-out 처리량이 먼저 천장에 닿는다.

전환 경로:
1. 1차로 `SSUBSCRIBE` 기반 샤드 한정 Pub/Sub으로 fan-out 분산
2. 그래도 부족하면 채널을 서버 인스턴스 단위로 바꾸고 라우팅 테이블 도입, 또는 전용 메시지 인프라로 교체

현 범위에서는 단일 Redis로 충분하므로 지금 전환하지 않을 뿐, **확장 천장이 어디인지는 분명히 인지하고 있다.**
