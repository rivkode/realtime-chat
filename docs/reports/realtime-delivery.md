# 실시간 라이브 전달

## 문제

유저 1이 보낸 메시지를 유저 2에게 실시간으로 전달해야 한다. 그런데 두 유저가 **서로 다른 채팅 서버**에 붙어 있을 수 있다(수평 확장의 전제). 발신 측 서버는 "유저 2가 지금 어느 서버에 있는지"를 모른다.

## 접근 — 세션 단위 Redis Pub/Sub 채널

Redis Pub/Sub의 채널을 사용자나 서버가 아니라 **`session_id`로** 잡는다.

- 유저 2가 어느 채팅 서버에 접속해 채팅방에 들어가면, 그 서버가 Redis 채널 `channel:session:{sessionId}`를 **구독**한다.
- 유저 1이 메시지를 보내면, 유저 1의 채팅 서버는 MongoDB에 저장한 뒤 같은 채널에 **발행**한다.
- 그 채널을 구독 중인 서버(= 유저 2가 붙은 서버)가 메시지를 받아 유저 2의 WebSocket으로 즉시 push한다.

핵심은 **유저 1의 서버가 "유저 2가 어느 서버에 있는지" 알 필요가 없다**는 점. `session_id`가 같으면 같은 채널을 통해 연결된다. 별도 라우팅 테이블도, 모든 서버에 뿌리는 브로드캐스트도 필요 없다. 구독/발행 모델 자체가 "위치를 모르고도 전달"을 해결한다.

구현:
- `chat-server`의 `SessionChannelSubscriber` — 세션 첫 연결 시 채널 동적 `SUBSCRIBE`, 마지막 끊김 시 `UNSUBSCRIBE`
- `SessionChannelPublisher` — 메시지 저장 후 `PUBLISH`
- STOMP destination `/topic/sessions/{id}`와 Redis 채널 `channel:session:{id}`가 세션 단위로 1:1 대응

## 왜 Kafka가 아닌가 — 두 층의 근거

### 1층 — 라이브 전달용으로 부적합

Kafka 컨슈머 그룹은 파티션을 멤버끼리 나눠 갖는 **"작업 분담"** 모델이다. 그런데 라이브 전달은 모든 채팅 서버가 전체 이벤트를 봐야 하는 **"브로드캐스트"**를 필요로 한다(누구에게 유저 2가 붙어 있을지 모르므로). 이 둘은 상반된다. Kafka로 브로드캐스트를 하려면 채팅 서버마다 별도 컨슈머 그룹을 줘 각자 전체 파티션을 읽게 해야 하는데, 이는 "한 번만 특정 서버로 가면 되는" 요구를 "모든 서버가 받아 대부분 버리는" 비효율로 만든다.

### 2층 — 비동기 파이프라인용으로도 불필요

`events` 단일 컬렉션 + 단일 도큐먼트 INSERT 구조라 큐로 분리할 비동기 작업 자체가 없다([비동기 처리 설계](async-processing.md)). 라이브 전달엔 부적합하고 비동기엔 쓸 데가 없어, 시스템에서 통째로 뺐다.

## "수백만 채널" 우려에 대한 답

세션마다 채널을 만들면 동시 활성 세션 수만큼 채널이 생긴다. Redis 채널과 Kafka 토픽은 같은 단어처럼 보이지만 다른 물건이다.

| | Kafka 토픽 | Redis Pub/Sub 채널 |
|---|---|---|
| 실체 | 물리적 — 디스크 로그 세그먼트, 파일 핸들 | 비물리적 — 구독자 목록을 담은 키 하나 |
| 생성 | 명시적으로 만들어야 함 | `SUBSCRIBE` 하는 순간 생기고, 마지막 구독자가 나가면 사라짐 |
| 빈 토픽/채널 | 디스크·메타데이터 점유 | 존재 자체를 안 함 |

Redis에서 채널 수는 "동시에 누가 구독 중인 세션의 수"만큼만 존재하며, 각 채널은 구독자 목록 하나라 가볍다. **채널 개수는 병목이 아니다.**

## 진짜 약점 — 인지하고 있는 한계

1. **단일 노드 fan-out 병목** — Redis Pub/Sub은 한 노드 안에서 동작한다. 채팅 서버가 N대면 N대 전부 같은 Redis에 연결해야 메시지가 닿는다. Redis 한 대가 fan-out 허브가 되어 단일 병목이다. 이것이 이 설계의 확장 천장이다([수평 확장](scalability.md)).
2. **best-effort** — 발행 순간 구독자가 없으면 메시지가 사라진다. 이는 의도된 것이며, 복구는 수신 측 Pull이 담당한다([재연결 정합성 & Pull 복구](reconnect-recovery.md)).

## 검토했으나 미채택 — 서버 인스턴스 단위 채널

채널을 `channel:chatserver-3`처럼 서버 인스턴스 단위로 잡고 "유저 B는 chatserver-3에 있다"는 매핑을 별도 저장하는 방식. 이 방식이 푸는 문제는 "세션 채널이 너무 많아지는 것"인데, 앞서 보았듯 Redis 채널은 가벼워 개수가 병목이 아니다 — *발생하지 않는 문제*를 푼다. 그 대가로 유저→서버 매핑 테이블의 stale 관리를 떠안는다. 현 범위에서 미채택.
