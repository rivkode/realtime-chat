# 재연결 정합성 & Pull 복구

## 문제

라이브 전달(Redis Pub/Sub)은 best-effort다. 발행이 유실되는 경우는 두 가지 — (a) 수신자가 그 순간 끊겨 있어 채널 구독자가 없거나, (b) Redis 자체가 다운된 경우. 재연결 후에도 데이터 정합성이 유지되어야 한다.

## 접근 — 복구 책임을 수신 측 Pull로

**핵심 원칙: 서버는 유실된 메시지를 추적하지도, 찾지도, 재전송하지도 않는다.**

"못 보낸 메시지를 스캔해 재전송"하는 push 방식 복구는 의도적으로 채택하지 않았다. 그것은 "어디까지 보냈는지 추적 + 누락분 탐색 + 재전송"을 직접 구현하는 일이고, 결국 Kafka가 영속 로그와 오프셋으로 하는 일을 손으로 다시 만드는 것이다. 발송 추적 테이블도, 누락 스캔 스케줄러도 두지 않는다.

대신 **복구의 책임은 수신 측에 있다.** 수신자가 데이터를 *당겨간다(pull)*. 트리거는 두 가지다.

### 트리거 1 — 재연결 시 resume

수신자는 마지막으로 받은 이벤트 `_id`를 보관한다. 재연결 시 `resume(session_id, last_event_id)`를 보내면, 서버는 MongoDB에서 `_id > last_event_id` 이벤트를 일괄 조회해 전송한 뒤 라이브 스트림으로 전환한다.

### 트리거 2 — 주기적 sync

수신자가 온라인인 채로 (b) Redis 장애로 메시지를 놓쳤고 그 후 재연결할 일이 없으면 누락을 영영 모를 수 있다. 이를 메우기 위해 클라이언트는 주기적으로 자기 `last_event_id`를 실어 보내고, 서버는 그 이후 이벤트가 더 있으면 마저 내려준다.

**두 트리거 모두 동일한 로직(`_id > last_event_id` 조회)을 쓴다.** 무엇이 왜 누락됐는지 구분할 필요가 없다 — 원인과 무관하게 "내가 가진 것 이후를 다 줘"가 항상 정답이다. 추가 컴포넌트는 0이며, 같은 진입점(`ResumeService.resume`)이 모든 누락을 일괄 처리한다.

구현: `chat-server`의 `ResumeService`, STOMP `SEND /app/sessions/{id}/resume`.

## 두 경로 분기 — 증분 vs 스냅샷

| 모드 | 조건 | 동작 |
|---|---|---|
| **INCREMENTAL** | `lastEventId`가 있고 catch-up 이벤트 수 ≤ 임계치 | `events.findAfter(sessionId, lastEventId, limit)` 그대로 응답 |
| **SNAPSHOT** | `lastEventId` 부재(앱 재설치·캐시 삭제) OR catch-up이 임계치 초과 | 가장 최신 스냅샷 + 이후 이벤트 fold → 현재 상태 + 새 `lastEventId` |

오래 끊긴 클라이언트가 수천 건을 일괄 전송받는 대신 스냅샷 기반 초기 로드로 우회한다. `(정상 resume) / (오래됨) / (분실)` 세 경우가 임계치를 경계로 두 경로로 깔끔하게 갈린다.

## catch-up과 라이브 스트림의 경계

catch-up 쿼리를 던지는 사이에 새 이벤트가 들어오면 catch-up 결과와 라이브 스트림 사이에 틈이나 겹침이 생길 수 있다. 설계서 §9.3이 정의한 정확한 순서는 — (1) 먼저 채널 SUBSCRIBE → 라이브 이벤트를 버퍼링, (2) catch-up 쿼리 실행·전송, (3) catch-up 마지막 `_id` 초과분만 버퍼에서 합류, (4) 라이브 직결 전환.

> **본 구현의 선택과 한계** — Spring `SimpleBroker`는 `SUBSCRIBE` 즉시 push를 시작해 서버측 버퍼링 윈도우를 만들기 까다롭다. 그래서 본 구현은 **클라이언트측 dedup**으로 대체했다 — UUIDv7 `_id`가 단조 증가하므로, 클라이언트가 catch-up 마지막 `_id` 기준으로 라이브에서 받은 이벤트 중 그보다 작거나 같은 것을 버리면 중복·누락 없이 정확히 이어붙는다. 서버측 버퍼링은 향후 보강 항목으로 남긴다.

## Pull 복구가 보장하는 것과 보장하지 않는 것

- **보장: 데이터 손실 방지.** 유저 1이 보낸 메시지가 MongoDB에 저장된 이상, 유저 2는 접속·sync 시점에 반드시 받는다.
- **보장 안 함: 실시간성.** Redis가 죽었는데 유저 2가 온라인이고 WebSocket이 멀쩡하면, 유저 2는 재연결할 이유가 없어 다음 주기적 sync 전까지 새 메시지를 모른다. 이 지연은 Pull 방식의 구조적 한계이며, 클라이언트 sync 주기 단축이 아니라 **Redis HA 구성(Sentinel)으로 장애 창 자체를 수 초로 줄여** 대응한다([장애 대응](fault-tolerance.md)).

## 채팅 서버 장애 시 복구

채팅 서버가 죽으면 죽은 서버의 상태를 다른 서버가 인계받지 않는다. 채팅 서버 인메모리에 있던 것은 살아있는 WebSocket 연결과 그 세션 매핑뿐 — 둘 다 영속 데이터가 아니라 *살아있는 연결의 부산물*이다. 복구는 클라이언트 재연결로 일어난다:

1. 채팅 서버 다운 → WebSocket 끊김 → 클라이언트가 자동 재연결
2. 로드 밸런서가 헬스체크 실패 서버를 분배 대상에서 제외 → 살아있는 서버로 라우팅
3. 새 서버가 `session_id`로 `SUBSCRIBE channel:session:{id}` (앞으로의 라이브)
4. 클라이언트가 `resume(last_event_id)` → 끊겨 있던 동안 놓친 메시지 일괄 수신

stateful 서버의 장애 복구는 "상태를 복구"하는 것이 아니라 애초에 "복구할 상태를 두지 않는" 설계로 푼다 — 채팅 서버 장애가 '상태 복구'가 아니라 '연결 재수립'으로 끝나는 이유다.
