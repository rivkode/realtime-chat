# 부하 테스트 결과

과제 명세 §5 가산점 — 부하 테스트 및 성능 측정. 설계서 §18 시나리오를 `e2e/load.js`로 자동화해 측정했다.

## 시나리오

설계서 §18의 샘플 채팅 데이터 생성 패턴:
1. user-1이 5초 동안 50ms 간격으로 메시지 1개씩 → 약 100개
2. user-2가 이어서 5초 동안 50ms 간격으로 → 약 100개
3. 결과적으로 한 세션에 약 200개의 이벤트가 시간순으로 쌓인다

50ms 간격은 사람의 실제 타이핑보다 빠른 부하로, 짧은 시간에 이벤트를 집중시켜 순서·중복·복원 동작을 압축 검증하기 위한 값이다.

실행: `./e2e/run.sh --load`

## 측정 1 — 메시지 처리 지연

client send → ACK 왕복 시간(ms). 로컬 환경, 1:1.

| 구간 | n | min | p50 | p95 | p99 | max | mean |
|---|---|---|---|---|---|---|---|
| 전체 | 200 | 5 | 15 | 23 | **27** | 36 | 14 |

서버측 처리 지연(Prometheus `chat.message.dispatch` `_sum`/`_count` 평균): chat-server-1 ~7.9ms, chat-server-2 ~7.6ms.

- p99 27ms — WS 수신부터 ACK까지의 왕복. 1:1·로컬 기준 충분히 낮다.
- 서버측 평균 ~7.7ms — UUIDv7 발급 + 단일 도큐먼트 INSERT + ACK. 단일 INSERT 구조라 락 경합 지점이 없는 효과.
- burst wall time 약 5.1s (이상적 5s) — 50ms 간격이 backpressure 없이 유지됨.

## 측정 2 — 순서 정합성

200건 송신 후 `events`의 `_id` ASC 정렬 결과가 송신 순서(`A-001…A-100, B-001…B-100`)와 **전수 일치**. UUIDv7 `_id`가 서버 수신 순서를 일관되게 정렬함을 확인.

## 측정 3 — 복원 시간과 스냅샷 임계치 N

`timeline?at=` 응답 시간을 누적 이벤트 건수별로 측정(각 3회 중앙값):

| 누적 이벤트 | 복원 시간 |
|---|---|
| 2,000 | 36ms |
| 5,000 | 42ms |
| 10,000 | 65ms |
| 20,000 | 141ms |

측정 범위(~20,000건)에서 1초에 도달하지 않았다. 선형 외삽 시 **약 167,000건에서 1초 도달** 추정.

### SNAPSHOT_THRESHOLD 산정

설계서 §12.3은 "처음부터 복원 시 1초를 넘기 시작하는 이벤트 수"를 기준으로 스냅샷 임계치 N을 역산하라 하고, 잠정값 N=500을 두되 측정으로 조정하라고 명시했다.

측정 결과 잠정 500은 **과도하게 보수적**이다 — 5,000건 복원이 ~42ms로 1초 SLA에 한참 못 미친다. N을 너무 작게 잡으면 스냅샷이 과다하게 찍혀 저장 비용·스케줄러 부하가 늘어난다.

**조정: `SNAPSHOT_THRESHOLD` 500 → 5,000.**
- 5,000건 복원 ~42ms로 1초에 충분히 안전
- 스냅샷 빈도가 1/10로 감소
- 외삽값 167,000(×0.7 마진 ≈ 117,000)은 로컬 측정 과신 위험이라 채택하지 않고 보수적으로 5,000

> **한계 명시** — 로컬 측정이라 네트워크 지연이 없고, 도큐먼트가 작으며, 샤딩이 없다. 운영 환경에서는 이 셋이 모두 복원 시간을 늘리므로 재측정이 필요하다. `SNAPSHOT_THRESHOLD`는 환경변수로 노출해 운영 측정 후 조정 가능하게 했다.

## 측정 4 — 다중 채팅 서버 라이브 전달

user-1(`chat-server-1`)과 user-2(`chat-server-2`)가 서로 다른 서버에 붙은 상태에서 200건 전부 양쪽으로 정상 전달. 서버측 `chat.event.delivered` 카운터로 확인.

## 도구

`e2e/load.js` — Node.js + `@stomp/stompjs`. k6는 STOMP 프로토콜을 native 지원하지 않아(WebSocket frame을 직접 STOMP로 조립해야 함) 이미 stompjs를 쓰는 Node 기반 도구로 통일했다. `functional`(`scenario.js`)과 `load`(`load.js`)를 `run.sh`의 `--load` 옵션으로 분리.
